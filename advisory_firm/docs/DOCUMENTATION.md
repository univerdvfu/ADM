# Документация: эмуляция БД инвестиционного консультирования на данных Мосбиржи

## 1. Назначение

Проект эмулирует базу данных фирмы, которая получает рыночные данные Московской биржи, хранит их,
проверяет и отдаёт аналитикам и клиентам. Это не биржа и не торговая система: торговый движок,
клиринг и надзор биржи в проект не входят.

Цель — показать, что база данных предметной области справляется со сложными задачами. Для этого
реализованы схемы в трёх хранилищах, загрузка реальных данных и 15 тестов, которые проверяют работу
БД на настоящих PostgreSQL и ClickHouse.

Стек, взятый из исходной презентации: **PostgreSQL**, **ClickHouse**, **MinIO**, **Airflow**.
Kafka не используется: консультанту нужны дневные бары и справочники, а не поток тиков в реальном времени.

## 2. Архитектура

```
API Мосбиржи ──► Airflow (DAG, будни 19:00) ──► MinIO (сырьё)
                                                   │
                                                   ▼
PostgreSQL ── выгрузка справочников ──► ClickHouse ◄── Загрузчик (контракт, часы торгов, допуск, дубли)
 (справочники, участники,   по белому списку        │            │
  клиенты, журнал,                                  │            └─ брак ──► карантин (PostgreSQL)
  карантин)                                         ▼
                                      свечи, сигналы, отчёты ──► аналитик, SQL
```

Наглядно: `docs/block_scheme.png` (схема) и `docs/how_it_works.gif` (анимация 8 шагов).

| Компонент | Роль |
|---|---|
| PostgreSQL 16 | реляционные данные: справочники, брокеры, заказчики, счета, клиенты фирмы, портфели, журнал рекомендаций, карантин |
| ClickHouse | ряды: дневные бары, сделки, котировки, минутные свечи, сигналы, журналы загрузки |
| MinIO | сырые ответы API биржи и пакеты сделок (бакет `raw-market`) |
| Airflow 2.10 | расписание: DAG `advisory_pipeline` по будням в 19:00, после закрытия торгов |

### Поток данных (DAG `advisory_pipeline`)

| Шаг | Что делает |
|---|---|
| `init` | создаёт схемы PostgreSQL и ClickHouse, если их нет |
| `fetch` | запрашивает историю и карточки бумаг у API Мосбиржи, кладёт сырьё в MinIO |
| `load` | читает сырьё из MinIO, загружает справочники в PostgreSQL, выгружает их в ClickHouse по белому списку, загружает бары |
| `check` | проверяет качество баров: `high ≥ low`, цена закрытия между минимумом и максимумом, данные не пусты |
| `recommend` | создаёт черновики рекомендаций по активным клиентам |

Повторный запуск безопасен: бары схлопываются по ключу `(ticker_id, session_id)`, пакеты сделок
пропускаются по `batch_id`, события дедуплицируются по `source_id + event_id`.

## 3. Модель данных

### 3.1. PostgreSQL (16 таблиц)

Файлы: `schema_pg.sql` (внешний контур) и `schema_advisory.sql` (консультирование).

**Справочники**

| Таблица | Назначение и ключевые правила |
|---|---|
| `issuers` | эмитенты: `issuer_id`, `name`, `country_code CHAR(2)` |
| `instruments` | `nominal_value NUMERIC(20,8)`, `currency CHAR(4)`; `instrument_type` — stock / future / option; `contract_term` (fixed / perpetual) только у фьючерсов, `exercise_style` (american / european) только у опционов; у срочного фьючерса дата погашения обязательна, у бессрочного запрещена, у акции производных признаков нет |
| `tickers` | тикер как отдельный объект: `ticker_id`, ссылка на инструмент, `ticker` уникален |
| `trading_sessions` | сессия: дата, начало и конец (с часовым поясом), площадка, статус |
| `session_instruments` | допуск инструмента к сессии: ключ `(session_id, ticker_id)`, лот, шаг цены, статус торгов |

**Участники (внешний контур источника; в аналитику не выгружается)**

| Таблица | Назначение и ключевые правила |
|---|---|
| `brokers` | брокеры, статус лицензии |
| `customers` | заказчик работает только через брокера (`broker_id NOT NULL`) |
| `owner_accounts` | отдельный обязательный аккаунт владельца; `ticker_id NOT NULL` — ссылка на объект; пара (заказчик, брокер) проверяется составным ключом |
| `client_requests` | поручения; пара `(session_id, ticker_id)` должна быть в `session_instruments` |

**Консультирование**

| Таблица | Назначение и ключевые правила |
|---|---|
| `advisory_clients` | клиент фирмы: псевдоним, риск-профиль (conservative / moderate / aggressive), горизонт, лимит доли позиции |
| `positions` | портфель: ключ `(client_id, ticker_id)`, количество не отрицательно |
| `corporate_events` | дивиденды и сплиты; у дивиденда обязательна сумма, у сплита коэффициент |
| `recommendations` | журнал рекомендаций; менять и удалять нельзя (триггеры PostgreSQL) |
| `recommendation_status_events` | статусы draft → approved / rejected → published; только добавление |

**Служебные**

| Таблица | Назначение |
|---|---|
| `ingest_jobs` | задание загрузки: пакет, источник, сырьё в MinIO, счётчики принято, дублей, отклонено |
| `quarantine` | отклонённые записи: номер строки и код правила, без копии полей |

### 3.2. ClickHouse (11 таблиц)

Файл: `schema.sql`. Связи логические: внешних ключей и уникальности ClickHouse не обеспечивает,
это делает загрузчик.

| Таблица | Назначение |
|---|---|
| `ref_sessions`, `ref_session_instruments` | справочники, выгруженные из PostgreSQL по белому списку; номинал `Decimal(20,8)`, валюта `FixedString(4)` |
| `market_trades` | сделки; ключ события `source_id + event_id`; партиции по месяцам |
| `market_quotes` | котировки bid / ask |
| `daily_bars` | дневные бары (основной ряд для консультирования); версии строк через `ReplacingMergeTree` |
| `agg_ohlcv_1m` | минутные свечи; ключ `ticker_id + session_id + minute`, сессии не смешиваются |
| `signals`, `recommendations`, `audit_log` | сигналы и журнал прежней версии (рекомендации основного журнала в PostgreSQL) |
| `ingest_batches`, `ingest_rejects` | журналы загрузки: пакеты и коды отклонений |

В ClickHouse нет ID брокеров, клиентов, счетов и заявок.

### 3.3. MinIO

Бакет `raw-market`: файлы вида `moex/<дата>/hist_<тикер>.json`, `sec_<тикер>.json` (ответы API как есть)
и `<batch_id>.jsonl` (пакеты сделок). Значения полей с ID участников перед сохранением заменяются на `***`.

## 4. Правила загрузки данных

Загрузчик (`analytics_firm/loader.py`) обрабатывает пакет сделок. Каждая запись проходит проверки;
при нарушении записывается только **код правила** (в `ingest_rejects` и `quarantine`), копия полей не сохраняется.

| Код правила | Что нарушено |
|---|---|
| `forbidden_field` | в записи есть user_id, owner_id, account_id, customer_id, broker_id, participant_id или client_id |
| `unknown_field`, `missing_field` | поле вне белого списка или не хватает обязательного |
| `empty_key`, `bad_ticker_id`, `bad_session_id`, `bad_time` | пустой ключ, неверный идентификатор или время |
| `bad_price` | цена не положительна или не умещается в `Decimal(20,8)` (до 12 цифр целой части и 8 дробных) |
| `bad_quantity` | количество не целое положительное |
| `foreign_source` | `source_id` записи не совпадает с источником пакета |
| `unknown_session`, `ticker_not_admitted_to_session` | сессии нет, или тикер не допущен к этой сессии |
| `session_closed` | сессия закрыта, новые сделки не принимаются |
| `outside_session_hours` | время сделки вне часов торгов сессии (границы включены) |

Дубли (`source_id + event_id`) не считаются нарушением: их число попадает в счётчик `duplicates`.
Пакет с уже виденным `batch_id` пропускается целиком.

### Итоги дня (дневные бары)

Дневные бары загружает DAG, а не `/api/ingest`, но проверяются они теми же правилами до записи (`ingest_bars` в `loader.py`,
`validate_bar` в `contract.py`): белый список полей, запрет ID участников, цены `Decimal(20,8)`, оборот `Decimal(30,8)`,
согласованность цен внутри бара, допуск бумаги к сессии. Бракованный бар **в `daily_bars` не попадает**: в карантин PostgreSQL
уходит номер строки и код правила, задание пишется в `ingest_jobs`.

| Код правила | Что нарушено |
|---|---|
| `forbidden_field`, `unknown_field`, `missing_field` | ID участника, лишнее или отсутствующее поле |
| `bad_price` | цена не положительная или не умещается в `Decimal(20,8)` |
| `high_below_low` | максимум ниже минимума |
| `price_outside_range` | открытие или закрытие вне диапазона минимум–максимум |
| `bad_volume`, `bad_count`, `bad_turnover` | объём, число сделок или оборот отрицательны или не числа |
| `bad_date` | дата не разобрать |
| `ticker_not_admitted_to_session`, `foreign_source` | бумага не допущена к сессии, источник чужой |

Задача `check` после загрузки остаётся второй линией защиты: проверяет уже записанные данные и роняет запуск, если что-то прошло.

### Открытие и закрытие биржи

1. Сессия открыта (10:00–18:50): сделки принимаются, расчётов по ней ещё нет.
2. Сделка до открытия или после окончания торгов отклоняется (`outside_session_hours`).
3. Закрытие сессии (`analytics_firm/sessions.py`): статус `closed`, затем считаются минутные свечи и сигналы.
4. После закрытия сделки отклоняются (`session_closed`).
5. DAG запускается в 19:00, после окончания торгов.

### Обезличивание

Отдельная задача (`analytics_firm/anonymize.py`) работает на стороне источника до выдачи данных:
белый список полей вместо репликации таблиц, псевдонимы — HMAC с секретом (обычный хеш ID
перебирается быстро). Ключ и таблица соответствий в аналитику не попадают.

### Время

Время сделок Мосбиржи — местное московское (UTC+3, без перехода на летнее). Окна сессий из PostgreSQL
переводятся в это время при выгрузке в ClickHouse. Пропуск этого шага сдвигал окно на 3 часа
и приводил к отклонению корректных сделок; ошибку нашли тесты.

## 5. Данные

**Реальные (Мосбиржа, публичный API ISS):** дневные бары за 64 торговые сессии по пяти бумагам
(SBER, GAZP, LKOH, ROSN, GMKN), карточки бумаг (лот, шаг цены, номинал, валюта). Сохранены в
`tests/fixtures/moex`, для живого запуска берутся из API.

**Выдуманные демо-данные:** брокеры, заказчики, аккаунты владельцев, поручения, клиенты фирмы, портфели,
дивиденды, котировки bid / ask. Они нужны только для показа структуры и помечены «демо».

**Ограничения источника:**
- публичный API отдаёт сделки пустыми; сделки торгового дня в демонстрации собраны по реальному бару (открытие, максимум, минимум, закрытие);
- дивиденды из API не получены;
- условия лицензии на данные Мосбиржи нужно проверить отдельно.

Файл `tests/test_db_complex.py`. Запускаются на настоящих PostgreSQL 16 и ClickHouse 26 (каждый тест
получает свою временную базу и удаляет её после себя).

|---|---|---|---|

| 5 | PostgreSQL | Последний статус записи через `DISTINCT ON` | published, rejected, draft ровно у своих записей |
| 6 | PostgreSQL | Оконные функции по дивидендам: накопление, рост, последнее | 10, 22, 37 и 5, 12; рост +20 % и +25 % |
| 7 | PostgreSQL | 100 000 позиций: индекс и сумма | `Index Scan`, сумма 520 150 000 совпала |

## 7. Сервис просмотра

`bash deploy/service.sh` → http://127.0.0.1:8765 (слушает только localhost).

| Вкладка | Что делает |
|---|---|
| Данные | список таблиц PostgreSQL и ClickHouse с числом строк, просмотр с постраничным листанием, объекты MinIO |
| Тесты | запуск 15 тестов, прогресс, статусы по тестам; для каждого суть, ожидаемый результат, запросы к БД по ходу выполнения, ошибка при падении, код теста; живой вывод pytest |
| Загрузка | наполнение баз данными Мосбиржи (сохранённые ответы или живой API), моделирование торгового дня, очистка баз |

API сервиса: `GET /api/status`, `/api/tables`, `/api/table`, `/api/minio`, `/api/tests`,
`/api/run/<id>`, `/api/job/<id>`; `POST /api/run`, `/api/seed`, `/api/reset`.
Произвольный SQL через сервис выполнить нельзя: имена таблиц проверяются по списку.

### Подать свой JSON

Описание всех запросов с примерами и кнопкой «Try it out»: **Swagger** на `/docs` (спецификация `/openapi.json`).

Любой пакет сделок можно отправить прямо в загрузчик через API и увидеть реакцию системы:

| Запрос | Что делает |
|---|---|
| `POST /api/ingest?dry=1` | разбор без записи: вердикт по каждой записи |
| `POST /api/ingest` | запись в базы; в ответе вердикты, карантин, что изменилось в таблицах и в MinIO |
| `POST /api/ingest?candles=1` | то же и пересчёт свечей |
| `POST /api/ingest/session?status=closed` (или `open`) | закрыть или открыть торговую сессию |
| `POST /api/ingest/reset` | очистить сделки и свечи |

Тело запроса — сам JSON: список записей (`source_id`, `event_id`, `ticker_id`, `session_id`, `event_time`, `price`, `quantity`)
или таблица `trades` в формате ISS Мосбиржи. Сделки попадают в отдельную сессию-песочницу 20990103 (SBER, 10:00–18:50),
реальные данные не затрагиваются. Готовые примеры и команды: `docs/examples/`.

Отчёт одной страницей: `bash deploy/demo.sh` → `demo/report.html`.

## 8. Развёртывание

Нужны: Linux или Ubuntu WSL, Python 3.12, Go (для сборки MinIO), доступ в интернет, свободные порты
8123 (ClickHouse), 39010 (MinIO), 8765 (сервис), 8080 (веб-интерфейс Airflow). Права sudo не нужны.

```bash
bash deploy/setup.sh        # установка, около 1 ГБ
bash deploy/start.sh        # запуск ClickHouse, MinIO, PostgreSQL (127.0.0.1)
bash deploy/service.sh      # сервис просмотра
bash deploy/airflow.sh test 2026-10-29    # прогон задач DAG
bash deploy/run_tests.sh tests/test_db_complex.py -vv
```

Переменные окружения (значения по умолчанию в `deploy/env.sh`): `CH_HOST`, `CH_PORT`,
`PG_DATA`, `PG_DSN`, `MINIO_ENDPOINT`, `MINIO_USER`, `MINIO_PASSWORD`. Данные и бинарники
лежат в `~/advisory-stack`. После перезагрузки компьютера сервисы запускаются заново через `start.sh`.

## 10. Что проверено и ограничения

**Проверено запуском:** все 15 тестов проходят; каждая из пяти задач DAG прошла по живому API Мосбиржи
(`airflow tasks test`); сервис просмотра запущен, загрузка данных, просмотр таблиц и запуск тестов
отработали; скрипты `start.sh` и `airflow.sh test` запускались из папки проекта.

**Не проверено или слабое:**
- на контейнере `setup.sh` прошёл с нуля, но скрипты и службы под него дорабатывались вручную по ходу (создание каталогов данных, PATH для Airflow);
- локальный `airflow dags test` в WSL завис; зато на контейнере Proxmox планировщик Airflow выполнил DAG целиком (ручной и один пропущенный по расписанию запуск, оба `success`); сам запуск по будням в 19:00 МСК дождаться не удалось;
- слайды презентации не просматривались в PowerPoint;
- права ролей реализованы в коде приложения, а не в правах БД;
- ClickHouse не проверяет ключи и уникальность, это делает загрузчик;
- таблицы `signals` и `recommendations` в ClickHouse — остаток прежней версии, их стоит удалить;
- учётные данные MinIO (`testadmin`) тестовые, для чего-либо кроме локальной проверки их надо заменить.

## 11. Глоссарий

| Термин | Значение |
|---|---|
| Сессия | торговый день на площадке с часами торгов и статусом |
| Допуск | запись «тикер торгуется в этой сессии» (`session_instruments`) |
| Бар | дневная свеча: open, high, low, close, объём, оборот |
| Свеча | минутная агрегация сделок по `ticker_id + session_id + minute` |
| Белый список | перечень полей, которые разрешено принимать и выдавать |
| Карантин | таблица отклонённых записей, хранит только код правила |
| Идемпотентность | повторная загрузка тех же данных не меняет результат |
| HMAC-псевдоним | идентификатор, полученный с секретным ключом; обратно не восстанавливается без ключа |
